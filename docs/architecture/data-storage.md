# MiniLMS — Технологии хранения данных

## Часть 1. Сущности системы

### 1.1. Перечень сущностей и их атрибуты

Сущности определены на основе функциональных требований (UC-01…UC-09), OpenAPI-спецификации и модели данных проекта.

**Пользователь (User)** id (UUID), email, fullName, passwordHash, role (learner / author / coordinator / admin), createdAt.

**Группа (Group)** id, name, memberCount. Связь «многие-ко-многим» с пользователями через промежуточную таблицу GroupMember (groupId, userId).

**Курс (Course)** id, title, description, status (draft / published), authorId → User, createdAt, updatedAt.

**Урок (Lesson)** id, courseId → Course, title, content (HTML/Markdown), order, externalLinks (массив URL). Примечание: связь с тестом хранится на стороне теста (Test.lessonId → Lesson). Поле testId в API-ответе вычисляется при выдаче, а не хранится как FK в таблице уроков, чтобы избежать циклической зависимости.

**Вложение (Attachment)** id, fileName, url, sizeBytes, mimeType. Связь с уроками — через промежуточную таблицу LessonAttachment (lessonId, attachmentId), т.к. один файл теоретически может использоваться в нескольких уроках.

**Тест (Test)** id, lessonId → Lesson, passingScore, maxAttempts (nullable).

**Вопрос (Question)** id, testId → Test, type (single_choice / multiple_choice / short_text), text, points, correctTextAnswer (nullable, для short_text).

**Вариант ответа (Option)** id, questionId → Question, text, isCorrect (bool). Хранится в отдельной таблице, т.к. у одного вопроса может быть 2–6 вариантов.

**Попытка теста (Attempt)** id, testId → Test, userId → User, score, maxScore, passed (bool), submittedAt. Неизменяема после создания (NFR-DATA-02).

**Ответ в попытке (AttemptAnswer)** id, attemptId → Attempt, questionId → Question, selectedOptionIds (массив UUID, для choice-вопросов), textAnswer (для short_text). Хранится в отдельной таблице, т.к. одна попытка содержит ответы на все вопросы теста.

**Назначение (Assignment)** id, userId → User, courseId → Course, groupId → Group, status (assigned / in_progress / completed / overdue), startDate, deadline.

**Прогресс по уроку (LessonProgress)** lessonId → Lesson, userId → User, status (not_started / in_progress / completed), completedAt.

**Уведомление (Notification)** id, userId → User, type (course_assigned / deadline_soon / overdue), title, message, courseId, read (bool), createdAt.

### 1.3. Характер взаимодействия с данными

**Транзакционные данные (OLTP)** — основной характер для MVP: Все сущности участвуют в коротких операциях: создать курс, отправить тест, назначить группе, обновить статус. Запросы затрагивают единицы–десятки строк, требуют ACID-гарантий (особенно попытки тестов и назначения).

**Аналитические данные (OLAP-подобные)** — вторичный характер: Отчёты по курсу/группе (UC-08) агрегируют данные: «сколько начали / завершили / просрочили». На масштабе MVP (до 50 человек в группе, до 100 курсов) это не требует отдельной аналитической системы — достаточно SQL-запросов с индексами к той же БД. При росте (тысячи пользователей, сотни групп) стоит выносить аналитику в отдельное хранилище (DWH или материализованные представления).

**Неструктурированные данные:** Вложения (PDF, изображения) — бинарные файлы, не участвуют в запросах по содержимому, хранятся отдельно от структурированных данных.

### 2.2. Обоснование решений

**Почему одна реляционная БД для большинства сущностей?**

Во-первых, масштаб MVP невелик. Все структурированные данные суммарно занимают менее 200 МБ в первый год. Любая современная РСУБД (PostgreSQL, MySQL) справляется с таким объёмом без усилий и с запасом на порядок.

Во-вторых, данные сильно связаны между собой. Попытка теста ссылается на тест, тест — на урок, урок — на курс, назначение связывает пользователя с курсом и группой. Эти связи естественно выражаются через внешние ключи. Документная или key-value БД потребовала бы дублирования данных или ручной синхронизации.

В-третьих, бизнес-логика требует ACID. Назначение курса группе (UC-06) должно быть атомарным. Фиксация попытки теста и обновление прогресса (NFR-DATA-01) должны быть в одной транзакции. Потеря данных при сбое недопустима.

**Почему уведомления тоже в реляционной БД, хотя допускают eventual consistency?**

На масштабе MVP (~30 000 уведомлений/год) выделять отдельное хранилище — избыточное усложнение. Одна таблица notifications с индексом по (userId, read) полностью закрывает потребности. При росте до сотен тысяч пользователей можно вынести уведомления в Redis (для быстрого счётчика непрочитанных) или в очередь сообщений.

**Почему вложения хранятся отдельно?**

Бинарные файлы (PDF, изображения) не участвуют в SQL-запросах, не нуждаются в транзакциях и занимают на порядки больше места, чем метаданные. Хранение их в БД раздувает таблицы, замедляет бэкапы и не даёт преимуществ.

На MVP допустимо простое файловое хранилище на сервере (директория + nginx для отдачи). Метаданные (имя файла, URL, размер, MIME-тип) хранятся в реляционной БД.

При масштабировании — переход на Object Storage (S3 / MinIO): автоматическая репликация, CDN-интеграция, версионирование, дешёвое хранение.

**Почему не документная БД для контента уроков?**

Контент урока (HTML/Markdown) — это одно текстовое поле внутри структурированной записи. Весь остальной контекст (порядок уроков, привязка тестов, внешние ключи на курс) требует реляционных связей. Хранить уроки в MongoDB ради одного текстового поля означало бы потерять целостность связей и получить проблемы с JOIN-запросами в отчётах.

### 2.3. Отчёты: OLTP или OLAP?

Отчёты по группе/курсу (UC-08) — это агрегация: подсчёт пользователей по статусам, прогресс, последний балл теста. Формально это OLAP-паттерн.

Однако на масштабе MVP (группа до 50 человек, NFR-PERF-02: отчёт за ≤ 0.5 сек) это решается обычными SQL-запросами с индексами:

- Индекс по (courseId, groupId, status) на таблице assignments

- Индекс по (userId, testId) на таблице attempts

- Пагинация по 50 строк (уже заложена в API)

Выносить аналитику в отдельное хранилище (DWH) имеет смысл при росте:

- Тысячи групп, десятки тысяч пользователей

- Запросы типа «динамика прохождения по когортам за полгода» (заложено в V3 roadmap)

- Отчёты начинают замедлять операционные запросы

Подтвердить момент перехода можно через метрики: если p95 отчётов превышает 2 секунды или отчёты создают > 30% нагрузки на БД — пора выделять OLAP.

### 2.4. Допущения и как их проверить

|Допущение|Как подтвердить|
|-|-|
|Среднее количество уроков в курсе ~ 10|Замерить на пилоте: avg(lesson_count) по курсам. Влияет на оценку объёма прогресса|
|Средний размер контента урока ~ 50 КБ|Замерить на пилоте: avg(length(content)) по таблице lessons|
|Средний размер вложения ~ 5 МБ|Статистика загрузок на пилоте: avg(sizeBytes) по таблице attachments|
|~3 уведомления на назначение (назначен + скоро дедлайн + просрочен)|Логировать количество уведомлений / количество назначений за первый месяц|
|Отчёты не создают значимой нагрузки на OLTP|Мониторинг: доля медленных запросов (> 500 мс) от /reports эндпоинтов|
|10 000 попыток/мес — достаточный запас|Метрика: count(attempts) за месяц пилота; алерт при > 8 000|
|Среднее количество вопросов в тесте ~ 5|Замерить: avg(question_count) по тестам. Влияет на объём AttemptAnswer|

### 2.5. Итоговая архитектура хранения (MVP)

```Plain Text
┌──────────────────────────────────────────────────────────────┐
│                      Реляционная БД                          │
│                   (PostgreSQL / MySQL)                        │
│                                                              │
│  users ─── groups ─── group_members                          │
│    │                                                         │
│  courses ─── lessons ─── tests ─── questions ─── options     │
│    │            │                      │                     │
│  assignments   lesson_progress    attempts ─── attempt_answers│
│                                                              │
│  notifications                                               │
│  attachments (метаданные) ─── lesson_attachments             │
└──────────────────────────────────────────────────────────────┘
           │
           │ url ссылается на
           ▼
┌──────────────────────────────────────────────────────────────┐
│                  Файловое хранилище                           │
│               (локальный диск на MVP)                         │
│            (S3 / MinIO при масштабировании)                   │
│                                                              │
│  /uploads/lessons/{lessonId}/{fileName}                       │
└──────────────────────────────────────────────────────────────┘
```

Это решение соответствует принципу «начни с простого» из лекции: PostgreSQL покрывает все потребности MVP и масштабируется до сотен тысяч записей. Polyglot persistence (добавление Redis для кэша, Elasticsearch для поиска, DWH для аналитики) — задача следующих версий, когда метрики покажут необходимость.
