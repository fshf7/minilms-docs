Нефункциональные требования

Категория: Безопасность и приватность​

NFR-SEC-01 — Хранение паролей только в виде хэша

  • Описание: пароли хранятся только как стойкий хэш; восстановление пароля реализуется только через сброс.

  • Приоритет: H

  • Обоснование: утечка “открытых” паролей ведёт к несанкционированному доступу, репутационному и юридическому ущербу.

NFR-SEC-02 — Защищённый транспорт (HTTPS)

  • Описание: весь трафик между клиентом и сервером идёт по HTTPS; токены/сессии не передаются по HTTP.

  • Приоритет: H

  • Обоснование: без HTTPS возможен перехват учётных данных и результатов обучения.

NFR-SEC-03 — Авторизация и контроль доступа (RBAC) на сервере

  • Описание: сервер проверяет права на каждом защищённом API-запросе; нельзя полагаться только на фронт.

  • Приоритет: H

  • Обоснование: иначе возможен доступ к чужим курсам/отчётам через прямые запросы.

NFR-SEC-04 — Защита от перебора паролей

  • Описание: ограничение частоты попыток входа + временная блокировка после N неудачных попыток.

  • Приоритет: M

  • Обоснование: без защиты повышается риск взлома слабых паролей.

Категория: Производительность​

NFR-PERF-01 — Время отклика ключевых операций

  • Описание: при нагрузке пилота 95-й перцентиль времени ответа API для: открыть курс/урок, отправить тест, открыть отчёт — ≤ 2 сек.

  • Приоритет: H

  • Обоснование: “тормоза” снижают завершение курсов и доверие координатора к системе.

NFR-PERF-02 — Время формирования отчёта для типовой группы

  • Описание: отчёт по группе до 50 пользователей и курсу до 20 уроков формируется ≤ 0.5 сек (95-й перцентиль).

  • Приоритет: H

  • Обоснование: если отчёты медленные, координатор возвращается к ручным таблицам.

Категория: Надёжность и восстановление​

NFR-REL-01 — Доступность на пилоте

  • Описание: доступность системы ≥ 99% в период пилота (кроме плановых работ).

  • Приоритет: M

  • Обоснование: простои срывают обучение и убивают доверие к продукту.

NFR-REL-02 — Резервное копирование и восстановление

  • Описание: ежедневный бэкап БД; хранение минимум 7 копий; целевые показатели: RPO ≤ 24ч, RTO ≤ 4ч.

  • Приоритет: H

  • Обоснование: потеря прогресса/попыток тестов делает систему непригодной для контроля обучения.

Категория: Ёмкость (Capacity)​

NFR-CAP-01 — Поддерживаемый объём данных и пользователей (для MVP)

  • Описание: система поддерживает без деградации: до 1 000 зарегистрированных, до 300 активных в неделю, до 100 курсов, до 20 уроков в курсе, до 10 000 попыток тестов в месяц.

  • Приоритет: M

  • Обоснование: без ёмкостных ориентиров легко получить “случайные” тормоза и падения на пилоте.

Категория: Масштабируемость​

NFR-SCAL-01 — Горизонтальное масштабирование бэкенда

  • Описание: бэкенд проектируется статeless (состояние не хранится в памяти одного инстанса); допускается запуск нескольких экземпляров за балансировщиком.

  • Приоритет: L (для MVP), но фиксируем как принцип

  • Обоснование: без этого рост пользователей потребует дорогих переделок архитектуры.

Категория: Наблюдаемость (Observability)​

NFR-OBS-01 — Логи и метрики для диагностики

  • Описание: система пишет структурные логи ключевых событий и ошибок; собирает метрики минимум: % ошибок 5xx, время ответа (p95), количество входов, количество отправок тестов.

  • Приоритет: M

  • Обоснование: без наблюдаемости невозможно быстро понять причину сбоев и доказать факт операций (назначение/попытка/отчёт).

Категория: Удобство использования (Usability)​

NFR-UX-01 — Порог освоения для учащегося

  • Описание: не менее 80% новых пользователей в пилоте способны: открыть назначенный курс → открыть урок → начать тест без инструктажа (проверка на 10 пользователях).

  • Приоритет: H

  • Обоснование: если интерфейс сложен, учащиеся не проходят обучение и растёт нагрузка на поддержку.

NFR-UX-02 — Адаптивность интерфейса

  • Описание: основные сценарии (курс/урок/тест/уведомления) корректно работают при ширине экрана от 360px.

  • Приоритет: M

  • Обоснование: без адаптивности часть пользователей не сможет учиться со смартфона.

Категория: Совместимость​

NFR-COMP-01 — Поддержка современных браузеров

  • Описание: корректная работа в последних версиях Chrome/Firefox/Safari/Edge.

  • Приоритет: M

  • Обоснование: проблемы совместимости увеличивают количество отказов и обращений.

Категория: Сопровождаемость (Maintainability)​

NFR-MAINT-01 — Документированный API-контракт

  • Описание: API документирован и синхронизирован с реализацией (единый контракт); изменения требуют обновления контракта.

  • Приоритет: H

  • Обоснование: без контракта интеграция фронта/бэка будет нестабильной и дорогой по времени.

NFR-MAINT-02 — Регрессионные проверки критичных правил

  • Описание: есть автотесты на критичные ограничения: доступ по ролям, лимит попыток теста, фиксация попытки, назначение курса группе.

  • Приоритет: M

  • Обоснование: без регресса система будет “ломаться” при каждом изменении.

Категория: Нормативно-правовые требования (комплаенс)​

NFR-LGL-01 — Соответствие требованиям обработки персональных данных (152-ФЗ)

  • Описание:

    1. система запрашивает согласие на обработку ПДн при регистрации;

    2. хранит только минимально необходимые ПДн (email, имя — опционально);

    3. есть политика хранения/сроки;

    4. предусмотрено удаление/обезличивание аккаунта по запросу администратора (в рамках MVP);

    5. доступ к ПДн ограничен ролями и логируется.

  • Приоритет: H

  • Обоснование: нарушение требований по ПДн ведёт к серьёзным юридическим последствиям и запрету эксплуатации системы в организациях.

Категория: Целостность данных (как НФТ, без описания бизнес-процесса)​

NFR-DATA-01 — Атомарность записи результатов

  • Описание: фиксация попытки теста и обновление прогресса выполняются атомарно (в одной транзакции), чтобы не возникали “полусохранённые” состояния.

  • Приоритет: H

  • Обоснование: иначе отчёты будут показывать некорректные статусы и результаты, что делает контроль обучения недостоверным.

NFR-DATA-02 — Неизменяемость завершённых попыток

  • Описание: завершённая попытка теста неизменяема; любые админ-исправления возможны только через отдельную операцию с аудитом.

  • Приоритет: H

  • Обоснование: без неизменяемости результаты можно подделать, отчётам нельзя доверять.
